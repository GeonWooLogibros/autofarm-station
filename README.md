# 오토팜 스테이션

「오토팜 스테이션」은 우주정거장의 온실에서 드론을 코드로 움직여 화분 재배를 자동화하는 웹 게임입니다. 스팀 게임 「농부는 대체되었다」의 구조를 본떠 만들었으며, 플레이어는 파이썬과 같은 문법으로 코드를 작성하고, 수확한 작물로 새 문법과 작물, 더 넓은 선반을 해금합니다. 마지막 해금 항목인 "완전 자동화"를 구입하면 엔딩 화면이 나타나고, 엔딩까지는 1~2시간이 걸립니다.

코딩을 처음 해 보는 사람도 진행할 수 있도록, 항목을 해금할 때마다 안내 캐릭터 인트가 설명과 예제 코드, 스스로 해 볼 목표를 보여 줍니다. 게임은 PC 브라우저와 키보드를 기준으로 만들었습니다.

## 게임 구성

게임을 열면 시작 화면이 먼저 나타납니다. 시작 화면에는 "시작하기"(저장된 진행이 있으면 "이어하기")와 "도전 과제" 버튼이 있습니다.

- **본편**: 위에서 설명한 해금 중심의 게임입니다. 위쪽 막대의 "처음 화면으로"를 누르면 진행을 저장하고 시작 화면으로 돌아갑니다. 자원 칸마다 최근 60초 동안의 수확량을 "분당 +12"와 같은 형식으로 보여 줍니다.
- **도전 과제**: 조건이 정해진 짧은 문제 8개입니다. 과제는 처음부터 모두 열려 있으며, 본편의 해금 상태와 관계없이 과제마다 정해진 문법과 함수만 쓸 수 있습니다. 과제를 끝내면 걸린 시간 또는 동작 횟수, 등급(동·은·금), 드론이 동작한 횟수, 코드의 줄 수를 보여 줍니다. 무작위 요소가 있는 과제는 서로 다른 배치 3개에서 모두 성공해야 하며, 기록은 세 번의 합입니다. 닉네임을 정하면 기록을 랭킹에 올리고 다른 사람의 기록과 비교할 수 있습니다. 랭킹에 연결할 수 없는 환경에서도 내 기록은 이 브라우저에 남습니다.

## 실행 방법

Node.js 20.19 이상이 필요합니다. 저장소 폴더에서 다음 명령을 차례로 실행합니다.

```bash
npm install     # 의존 패키지를 설치합니다.
npm run dev     # 개발 서버를 시작합니다. 터미널에 표시된 주소를 브라우저에서 엽니다.
npm test        # 자동 테스트를 모두 실행합니다.
```

`npm run build`는 타입 검사를 한 다음 `dist/` 폴더에 배포용 파일을 만듭니다.

## 테스트

- `npm test`는 `tests/` 아래의 일반 테스트를 모두 실행합니다. 균형 테스트와 이전 판의 저장 데이터를 불러오는 테스트(`tests/progress/saveCompat.test.ts`)도 포함됩니다.
- `npm run test:rules`는 Firestore와 Auth 에뮬레이터를 띄워 `tests-rules/`의 테스트를 실행합니다. 보안 규칙과 Firebase 구현을 확인하는 테스트이며 `npm test`에는 포함되지 않습니다. 에뮬레이터를 실행하려면 Java가 필요하고, Java 17에서 동작하도록 `firebase-tools`는 14.27.0 버전으로 고정되어 있습니다. 자세한 내용은 아래의 "랭킹과 Firebase" 절에 있습니다.
- `npx tsc --noEmit`은 타입만 검사합니다.

## 저장 키

게임이 진행과 기록을 저장하는 `localStorage` 키는 다음 두 개입니다. 본편은 저장 데이터가 손상되었을 때 원본을 보관하는 `gardener-replaced:save:corrupt` 키도 쓰며, `gardener-replaced:`로 시작하지 않는 키는 읽거나 쓰거나 지우지 않습니다.

| 키 | 내용 |
| --- | --- |
| `gardener-replaced:save:v1` | 본편의 진행 상황입니다. 처음부터 다시 시작하려면 게임의 설정 화면에서 "처음부터 다시 시작하기"를 누릅니다. |
| `gardener-replaced:challenges:v1` | 도전 과제의 닉네임, 과제별 최고 기록, 편집 중인 코드, 안내를 본 과제의 목록입니다. 본편의 "처음부터 다시 시작하기"는 이 데이터를 지우지 않습니다. |

저장할 수 없는 브라우저(저장소가 막혀 있는 경우)에서는 화면을 떠나지 않는 동안에만 진행과 기록이 메모리에 유지됩니다.

## 배포용 빌드

이 게임은 두 가지 방법으로 배포합니다. 공개 사이트는 GitHub Pages에 올리며, 그 방법은 "처음 설정하기" 절의 6번에 있습니다. Claude 아티팩트에는 HTML 파일 하나로 만들어 올리며, 이 절은 그 파일을 만드는 방법을 설명합니다. 게임 저장소들이 함께 쓰는 `../tools/build-artifact.mjs`가 Vite로 빌드한 스크립트와 스타일을 파일 하나에 합칩니다. 그림과 소리는 Vite가 data URI로 바꿔 스크립트 안에 넣으므로, 만들어진 파일은 다른 파일 없이 혼자서 실행됩니다. 개발 서버(`npm run dev`)에서도 SVG 그림은 Vite가 data URI로 바꿔 넣으므로, 화면의 그림 주소는 개발 중에도 `data:image/svg+xml`로 시작합니다. 소리(MP3)만 개발 서버에서 별도의 파일로 제공되고, 배포용 빌드에서는 그림과 같이 data URI로 들어갑니다. `build.assetsInlineLimit` 설정은 `vite.config.ts`에 있습니다.

```bash
node ../tools/build-artifact.mjs . "오토팜 스테이션" <출력 파일 경로>
```

출력 파일은 저장소 바깥의 임시 폴더에 두는 것을 권장합니다. 만들어진 파일의 크기는 약 1.7MB입니다. 이 파일은 Claude 아티팩트에 올리는 형식에 맞추어 `<title>`, `<style>`, 본문, `<script>`만 담고 있으며, 브라우저에서 `file://` 주소로 직접 열어도 실행됩니다. Firebase 코드도 같은 스크립트에 들어 있으므로 빌드 결과에는 js 파일 1개와 css 파일 1개만 있어야 하며, 코드에서 동적 `import`를 쓰지 않습니다. 글꼴만 Google Fonts에서 내려받고, 그 밖의 외부 요청은 랭킹 설정값이 들어 있을 때의 Firebase 서버뿐입니다. 아티팩트에서는 외부 서버와 통신할 수 없으므로 랭킹이 꺼진 것처럼 동작합니다.

## 폴더 구조

소스 코드는 `src/` 아래의 다섯 부분으로 나뉘어 있습니다. 의존 방향은 `ui → progress → sim`, `ui → lang`, `progress → lang`, `ui → online`, `online → progress`(자료형만)이고, 반대 방향으로는 참조하지 않습니다. `lang`, `sim`, `progress`는 DOM, 현재 시각, 무작위 함수를 쓰지 않습니다.

| 폴더 | 역할 |
| --- | --- |
| `src/lang` | 파이썬 문법의 일부를 해석하는 실행기입니다. 소스 코드를 토큰과 구문 트리로 바꾸고, 잠긴 문법을 검사하고, 틱 예산만큼씩 나누어 실행하며, 오류를 줄 번호와 한국어 문장으로 알려 줍니다. |
| `src/sim` | 화면과 분리된 온실 시뮬레이션입니다. 선반 칸, 작물의 성장, 수분, 자원과 작물별 특수 규칙을 계산하며, 균형에 관련된 수치는 `balance.ts`에 모여 있습니다. |
| `src/progress` | 게임의 진행을 담당합니다. 해금 항목의 정의와 구입 처리, 드론 함수와 시뮬레이션의 연결, 안내 문구, 저장과 불러오기가 여기에 있습니다. 도전 과제의 정의(`challenges.ts`), 한 번의 실행(`challengeRun.ts`), 화면 없이 하는 심사(`challengeJudge.ts`), 과제 데이터의 저장(`challengeSave.ts`), 분당 수입 계산(`income.ts`)도 여기에 있습니다. |
| `src/online` | 랭킹 서비스입니다. 서비스의 인터페이스와 서버에 닿지 않을 때 쓰는 빈 구현(`ranking.ts`), Firebase를 쓰는 구현(`firebaseRanking.ts`), 설정값(`firebaseConfig.ts`), 기록을 올리는 작업의 줄 세우기(`uploads.ts`)가 있습니다. `ui`를 참조하지 않습니다. |
| `src/ui` | 화면을 담당합니다. 코드 편집기, SVG로 그리는 온실, 해금 화면, 안내 말풍선, 설명서, 설정, 효과음이 여기에 있습니다. 시작 화면(`startScreen.ts`), 과제 목록(`challengeList.ts`), 과제 화면(`challengeApp.ts`), 랭킹 화면(`rankingPanel.ts`), 화면 전환기(`router.ts`)도 여기에 있습니다. |

`tests/` 폴더는 `src/`와 같은 구조로 나뉘어 있고, 에뮬레이터가 필요한 테스트는 `tests-rules/`에 따로 있으며, `tests/model/scripts.ts`에는 균형 테스트가 사용하는 모범 코드가 있습니다. 설계 문서는 `docs/superpowers/specs/`에 있습니다.

## 처음 설정하기

저장소를 새로 받아 랭킹과 공개 사이트를 처음 여는 사람이 한 번만 하는 일입니다. 랭킹 없이 게임만 실행하려면 이 절을 건너뛰고 "실행 방법"만 따르면 됩니다. 아래에 적은 Firebase 콘솔의 단추와 메뉴 이름은 이 문서를 쓴 때의 것이며, 콘솔이 바뀌면 이름과 위치가 달라질 수 있습니다.

1. **Firebase 프로젝트 만들기**: [Firebase 콘솔](https://console.firebase.google.com/)에서 "프로젝트 추가"를 눌러 프로젝트를 만듭니다. Google 애널리틱스는 쓰지 않으므로 꺼도 됩니다. 요금제는 무료(Spark)로 충분합니다.
2. **익명 로그인 켜기**: 콘솔의 Authentication에서 "시작하기"를 누르고, "로그인 방법" 탭에서 "익명"을 사용 설정합니다.
3. **Firestore 데이터베이스 만들기**: 콘솔의 Firestore Database에서 "데이터베이스 만들기"를 누릅니다. 위치는 플레이어와 가까운 곳(예: 서울 `asia-northeast3`)을 고르고, 모드는 "프로덕션 모드"를 고릅니다. 위치는 만든 뒤에 바꿀 수 없습니다. 프로덕션 모드는 모든 읽기와 쓰기를 거부하는 규칙으로 시작하므로, 5번에서 규칙을 배포하기 전에는 랭킹이 동작하지 않습니다.
4. **웹 앱을 추가하고 설정값 넣기**: 콘솔의 프로젝트 설정에서 웹 앱(`</>`)을 추가합니다. Firebase 호스팅은 쓰지 않으므로 선택하지 않습니다. 표시된 `firebaseConfig`에서 `apiKey`, `authDomain`, `projectId`, `appId` 네 값을 복사해 `src/online/firebaseConfig.ts`의 `FIREBASE_CONFIG`에 넣고 커밋합니다. 이 값은 공개해도 되는 값입니다.
5. **규칙과 색인 배포하기**: 저장소 폴더에서 `npx firebase login`으로 로그인한 뒤 `npx firebase deploy --only firestore --project <프로젝트 id>`를 실행합니다. 이 명령은 `firestore.rules`와 `firestore.indexes.json`을 함께 올립니다. 색인은 만들어지는 데 몇 분이 걸릴 수 있습니다. 규칙의 내용과 테스트 방법은 아래의 "랭킹과 Firebase" 절에 있습니다. 규칙이 받는 문서의 필드는 기록이 쌓인 뒤에는 바꾸기 어려우므로, 배포하기 전에 `npm run test:rules`가 통과하는지 확인합니다. 또한 규칙을 배포하기 전에 Firestore의 `challenges` 아래에 `nickAt` 필드가 없는 옛 문서가 없는지 확인합니다. 그런 문서는 새 규칙에서 갱신할 수 없으므로 콘솔에서 지우거나 `nickAt`을 넣어 줍니다.
6. **GitHub Pages 켜기**: GitHub 저장소의 Settings → Pages에서 Source를 "GitHub Actions"로 바꿉니다. 그 뒤로는 `main` 브랜치에 올릴 때마다 `.github/workflows/pages.yml`이 `npm ci`, `npm test`, `npx tsc --noEmit`, `npx vite build --base ./`를 차례로 실행하고 `dist` 폴더를 배포합니다. 저장소의 Actions 탭에서 워크플로를 직접 실행할 수도 있습니다. 에뮬레이터가 필요한 `npm run test:rules`는 워크플로에서 실행하지 않으므로, 규칙을 고쳤을 때에는 올리기 전에 직접 실행합니다.
7. **배포한 주소에서 확인하기**: 워크플로가 끝나면 Actions 탭의 실행 결과에 표시되는 주소(`https://<계정>.github.io/<저장소 이름>/`)를 엽니다. "도전 과제"에서 닉네임을 정하고 1번 과제를 성공시킨 다음, 다음 세 가지를 확인합니다.
   - 결과 화면에 "랭킹에 올렸습니다."가 나옵니다. "랭킹에 올리지 못했습니다."가 나오면 다음 가운데 하나일 수 있습니다: 규칙이나 색인이 배포되지 않았거나, 익명 로그인이 꺼져 있거나, `firebaseConfig.ts`의 설정값이 틀렸거나, 통신에 문제가 있는 경우입니다. 어느 쪽인지는 브라우저 개발자 도구의 콘솔과 네트워크 탭에 나온 오류로 확인합니다.
   - "랭킹 보기"를 누르면 내 닉네임과 기록이 있는 줄이 보입니다. 기록은 올라갔는데 랭킹 화면에 "지금은 랭킹에 연결할 수 없습니다."가 나오면 색인이 아직 만들어지지 않은 것입니다.
   - Firebase 콘솔의 Firestore Database에서 `challenges/c01-first-v1/scores/<uid>` 문서에 `nickname`, `score`, `actions`, `lines`, `at`, `nickAt` 여섯 필드가 있습니다.

익명 로그인이 배포한 주소에서만 거부된다면, 콘솔의 Authentication → 설정 → 승인된 도메인에 `<계정>.github.io`를 추가합니다.

## 랭킹과 Firebase

도전 과제의 랭킹은 Firebase(Firestore와 익명 로그인)로 동작합니다. 소스는 `src/online/`에 있고, 화면은 `src/online/index.ts`의 `createRanking()`이 돌려주는 서비스만 사용합니다.

- **설정값**: Firebase 콘솔에서 웹 앱을 만든 뒤 `apiKey`, `authDomain`, `projectId`, `appId`를 `src/online/firebaseConfig.ts`의 `FIREBASE_CONFIG`에 넣습니다. 이 값은 공개해도 되는 값이며, 보호는 `firestore.rules`가 맡습니다. 값이 `null`이면 랭킹만 꺼지고 나머지 기능은 모두 동작합니다.
- **보안 규칙과 색인**: `firestore.rules`와 `firestore.indexes.json`에 있습니다. 규칙 안에는 과제별 점수의 범위 표(하한 `min`, 상한 `max`, 점수가 그 배수여야 하는 값 `step`)가 있습니다. 이 표는 `src/progress/challenges.ts`의 정의(`minScore`, 제한 시간 × 시드 수, 시간으로 재는 과제인지)와 같아야 하며, 다르면 `npm test`의 `tests/online/rulesFloors.test.ts`가 알려 줍니다.
- **규칙 테스트**: `npm run test:rules`는 Firestore와 Auth 에뮬레이터를 띄워 규칙과 Firebase 구현을 확인합니다. 에뮬레이터는 Java가 필요하며 포트 8790(Firestore)과 9099(Auth)를 사용합니다. 이 테스트는 `npm test`에 포함되지 않습니다. 최신 `firebase-tools` 15.x는 Java 21 이상을 요구하므로, Java 17에서도 도는 마지막 주 버전인 14.27.0으로 고정했습니다. Java 21 이상을 설치했다면 `firebase-tools`를 올려도 됩니다.
- **배포**: `npx firebase login`을 한 뒤 `npx firebase deploy --only firestore --project <프로젝트 id>`를 실행하면 규칙과 색인이 올라갑니다. Firebase 콘솔의 규칙 탭에 `firestore.rules`의 내용을 붙여 넣어도 됩니다. 색인은 콘솔에서 만들거나, 위 명령으로 올립니다. 프로젝트를 처음 만드는 순서는 위의 "처음 설정하기" 절에 있습니다.
- **무료 한도**: 하루 읽기 50,000건, 쓰기 20,000건, 저장 1GiB입니다. 랭킹 화면을 한 번 열면 읽기가 약 21건 발생하며, 같은 과제의 결과는 60초 동안 다시 읽지 않습니다.
- **화면에서 동작 확인**: 개발 서버(`npm run dev`)와 에뮬레이터(`npx firebase emulators:start --only firestore,auth --project demo-autofarm`)를 함께 실행하고, 브라우저 주소 끝에 `#emu`를 붙여 열면 랭킹이 에뮬레이터에 연결됩니다. 이 기능은 개발 서버에서만 켜지며 배포용 빌드에는 들어가지 않습니다.
- **동작 방식**: 플레이어는 닉네임(2~10자)만 정합니다. Firebase 익명 로그인으로 만드는 계정은 랭킹 화면을 열거나 기록을 올릴 때 처음 만들어지고, 브라우저(IndexedDB)에 유지됩니다. 기록은 과제마다 하나씩 줄을 세워 올리며, 올리지 못한 기록은 다음에 과제 목록을 열 때 다시 올립니다. 제출한 코드는 본인만 읽을 수 있는 문서(`private/code`)에 저장됩니다. 제출한 코드는 기록을 새로 올리거나 더 좋은 기록으로 바꾸는 요청에서만 함께 쓸 수 있습니다. 닉네임을 바꾸면 이미 올린 기록을 다시 올려 서버의 닉네임을 고칩니다. 보안 규칙은 닉네임을 정한 뒤 60초가 지나야 다시 바꾸게 해 주므로, 그보다 일찍 바꾼 닉네임은 60초가 지난 뒤에 과제 목록을 열 때 서버에 반영됩니다. 보안 규칙의 닉네임 길이 검사는 2~40자이며, 정확한 2~10자 검사는 클라이언트가 합니다.

## 도전 과제를 추가하거나 수치를 바꾸는 방법

과제의 정의는 `src/progress/challenges.ts`의 `CHALLENGES` 목록에 있습니다. 과제의 조건이나 수치를 바꾸거나 새 과제를 추가할 때에는 다음을 차례로 합니다.

1. **판 번호 올리기**: 과제의 `id` 끝에 있는 판 번호를 올립니다(예: `c05-water-v1` → `c05-water-v2`). 판 번호가 바뀐 과제는 랭킹과 내 기록이 새로 시작됩니다. `firestore.rules`의 범위 표와 `tests/model/challengeSolutions.ts`의 `SOLUTIONS` 키에도 같은 `id`가 있으므로 함께 바꿉니다.
2. **기준 풀이 고치기**: `tests/model/challengeSolutions.ts`에 과제마다 단순한 풀이와 잘 다듬은 풀이가 있습니다. 조건이 바뀌면 두 풀이가 여전히 성공하는지 확인하고 필요하면 고칩니다.
3. **균형 테스트 실행**: `npx vitest run tests/challengeBalance.test.ts`가 기준 풀이를 실행해 등급 기준(금·은·동), 제한 시간, 하한이 `challenges.ts`의 값과 같은지 확인합니다. 실패하면 출력된 기록을 보고 `challenges.ts`의 값을 4.4절의 규칙(설계 문서)에 맞게 고칩니다. 본편의 수치(`balance.ts`, `unlocks.ts`)를 바꾸었을 때에도 이 테스트가 실패할 수 있습니다.
4. **하한과 상한 고치기**: 하한은 그보다 좋은 기록이 나올 수 없음을 증명할 수 있는 값이어야 합니다. `challenges.ts`의 `minScore`를 고치고, 같은 값을 `firestore.rules`의 범위 표의 `min`에 적습니다. 제한 시간이나 시드 수를 바꾸었다면 표의 `max`도 고칩니다. 시간으로 재는 과제의 `max`는 제한 시간 × 시드 수이고, 횟수로 재는 과제의 `max`는 제한 시간 안에 할 수 있는 동작의 수(제한 시간 ÷ 동작 하나의 시간. 동작 하나는 500ms ÷ 드론 속도 배율) × 시드 수입니다. `step`은 시간으로 재는 과제이면 50, 횟수로 재는 과제이면 1입니다. `tests/online/rulesFloors.test.ts`가 세 값이 `challenges.ts`와 맞는지 확인합니다.
5. **규칙 테스트와 배포**: `npm run test:rules`로 규칙을 확인한 다음, "랭킹과 Firebase" 절의 방법으로 규칙을 배포합니다. 규칙을 배포하기 전에 새 판의 기록을 올리면 서버가 거부합니다.

## 해금 비용을 조정하는 방법

해금 비용은 `src/progress/unlocks.ts`의 `UNLOCKS` 목록에 있고, 작물의 성장 시간과 심는 비용, 수확량은 `src/sim/balance.ts`에 있습니다. 값을 바꾼 뒤에는 균형 테스트를 실행하여 게임이 여전히 끝까지 진행되는지 확인합니다.

```bash
npx vitest run tests/balance.test.ts
VITE_BALANCE_LOG=1 npx vitest run tests/balance.test.ts   # 항목마다 걸린 시간을 함께 출력합니다.
```

균형 테스트는 `tests/model/scripts.ts`에 적힌 모범 코드를 실제 실행기와 시뮬레이션으로 실행하면서, 정해진 순서대로 항목을 구입합니다. 그리고 모범 코드가 오류 없이 엔딩까지 진행하는지, 어느 항목도 모으는 데 12분을 넘기지 않는지, 엔딩까지 걸리는 시간이 40분에서 70분 사이인지를 검사합니다. 실제 플레이어는 모범 코드보다 느리게 진행하므로, 이 범위에 들어오면 실제 플레이 시간은 1~2시간이 됩니다.

새 문법이나 함수를 추가하여 단계가 달라졌다면 모범 코드와 구입 순서(`BUY_ORDER`)도 함께 고쳐야 합니다. 안내 문구에 나오는 숫자는 `balance.ts`와 `unlocks.ts`의 값에서 가져오므로 따로 고치지 않아도 되지만, 문구를 고쳤다면 `tests/progress/guide.test.ts`도 다시 실행합니다.

## 에셋 출처

그림과 효과음은 코드모스 에셋 창고에서 내려받은 파일이며, `src/assets/codmos/`에 들어 있습니다. 파일마다의 에셋 ID와 내려받기 주소, 게임에서 쓰는 곳은 `assets/SOURCES.md`에 기록되어 있습니다. 코드모스에 게임을 게시할 때에는 이 목록을 게시물의 사용 에셋 항목에 넣습니다.

파일을 다시 내려받으려면 다음 명령을 실행합니다. 내려받을 파일의 목록은 `scripts/fetch-assets.mjs`의 `ASSETS`에 있으므로, 에셋을 추가하거나 바꿀 때에는 이 목록과 `assets/SOURCES.md`를 함께 고칩니다.

```bash
node scripts/fetch-assets.mjs
```

선반, 온실 배경, 물탱크, 화물칸, 해금 화면은 에셋 창고의 그림이 아니라 코드에서 SVG로 직접 그린 것입니다.
